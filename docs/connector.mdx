## Availability

C1 only integrates with the Salesforce editions with API access: Salesforce Enterprise, Unlimited, Developer, and Performance editions. 

You cannot use this connector successfully with Group or Essentials editions, or with Professional edition without an API add-on. 

Learn more about which Salesforce editions support API access in the [Salesforce documentation](https://help.salesforce.com/s/articleView?id=000385436&type=1).

The Salesforce connector supports [automatic account provisioning](/product/admin/account-provisioning).

This connector deprovisions accounts by deactivating them. Salesforce does not permit deleting a user record, so C1 sets the account inactive and the record stays in your Salesforce org.

A Salesforce user holds at most one role and one profile. Granting either one replaces the assignment the user already had, so the previous role or profile stops appearing in C1 after the next sync.

**Territories are opt-in and disabled by default. Enable the Territory resource type in C1 to sync them, and enable Enterprise Territory Management 2.0 in your Salesforce org. If Enterprise Territory Management 2.0 is not enabled, the connector returns an error when attempting to sync territories. Only territories belonging to your org's Active territory model sync, and territory role entitlements come from the active `RoleInTerritory2` picklist values.**

***Agents (Agentforce agents and Einstein Bots, backed by the `BotDefinition` object) are opt-in and disabled by default. Enable the Agent resource type in C1 to sync them. Agentforce or Einstein Bots must be enabled in your Salesforce org; otherwise the connector skips agents cleanly.**

### Optional fields for custom validation rules

Some Salesforce orgs have custom validation rules that require additional fields to be set when creating a user (for example, a rule that requires `FederationIdentifier` for SSO).

To add an optional field mapping in C1, use the exact Salesforce field API name as the mapping key (for example, `FederationIdentifier`, `Department`, `CommunityNickname`) allowing you to satisfy any validation rule.

*You have the option to sync user accounts that use non-standard licenses. 

[This connector syncs non-human identities](/product/admin/nhi) and displays them on the **Identities overview** dashboard.

### Permission set group grants

The connector syncs two types of grant relationships for Permission Set Groups (PSGs):

- **PSG → User grants**: If a user is assigned to a Permission Set Group (via a `PermissionSetAssignment` record in Salesforce), C1 emits a `member` grant linking that user to the PSG. These grants appear on the PSG resource's Grants tab in C1.

- **PSG → Permission Set grants**: If a Permission Set is a component of a Permission Set Group (via a `PermissionSetGroupComponent` record), C1 emits an `assigned` grant on the Permission Set resource with the PSG as the principal. These grants support transitive access expansion: users who are members of a PSG are automatically shown as having access to all Permission Sets within that PSG, enabling access reviews at the PSG level.

<Note>
PSG → User grants require at least one `PermissionSetAssignment` record in Salesforce where the target is a Permission Set Group. If your Salesforce instance assigns access only through individual Permission Sets, PSG → User grants will not appear. PSG → Permission Set grants are unaffected: they come from `PermissionSetGroupComponent` records.
</Note>

### Connector actions

Connector actions are custom capabilities that extend C1 automations with app-specific operations. You can use connector actions in the [Perform connector action](/product/admin/automations-steps-reference#perform-connector-action) automation step.

| Action name | Additional fields | Description |
|-------------|-------------------|-------------|
| update_user_status | `resource_id` (string, required): the Salesforce User record ID, 15 or 18 characters beginning with `005`, which is the account's resource ID in C1 <br/>`is_active` (Boolean, required) | Updates a Salesforce user's status to active or inactive |

## Gather Salesforce credentials 

Configuring the connector requires you to pass in credentials generated in Salesforce. Gather these credentials before you move on. 

<Warning>
The connector user must have the **API Enabled** and **Manage Users** system permissions. If syncing connected apps, also add **Customize Application**. If using provisioning, also add **Manage Roles**. If you authenticate with a username and password, also add **Use Any API Auth**.
</Warning>

### Enable API access and permissions for your Salesforce user

Before you begin, make sure that the Salesforce user who will set up the integration with C1 has the required system permissions. The recommended approach is to create a Permission Set and assign it to the connector user.

<Steps>
<Step>
Log into Salesforce as an Administrator. Click the gear icon and select **Setup**. 
</Step>
<Step>
Search for "permission sets" and select **Permission Sets**.
</Step>
<Step>
Click **New** to create a permission set (for example, "C1 Connector Access").
</Step>
<Step>
In the permission set, click **System Permissions**, then click **Edit**.
</Step>
<Step>
Enable **API Enabled** and **Manage Users**. If syncing connected apps, also enable **Customize Application**. If using provisioning, also enable **Manage Roles**. If you authenticate with a username and password, also enable **Use Any API Auth**.
</Step>
<Step>
Click **Save**.
</Step>
<Step>
Click **Manage Assignments**, then **Add Assignment** to assign the permission set to the connector user.
</Step>
</Steps>
Your connector user now has the required permissions to sync Salesforce data.

### Create a Salesforce External Client App for JWT Bearer

Use these instructions if you want to authenticate using a signed JWT assertion and a private key.

<Steps>
<Step>
Log into Salesforce as an Administrator. Click the gear icon and select **Setup**.
</Step>
<Step>
Search for "External Client App Manager" and select **External Client App Manager**.
</Step>
<Step>
Click **New External Client App**.
</Step>
<Step>
Fill in the basic information:
- **External Client App Name**: a name of your choice (for example, `baton-jwt`)
- **Contact Email**: your email address
</Step>
<Step>
Expand **OAuth Settings** and configure the following:
- **Callback URL**: enter any valid URL
- **Selected OAuth Scopes**: add **Full access (full)**, **Manage user data via APIs (api)**, and **Perform requests at any time (refresh_token, offline_access)**
- Under **Flow Enablement**, check **Enable JWT Bearer Flow**. A **Certificate Upload** field will appear — upload your certificate (`.pem`). You will need the corresponding private key (`.pem`) later when configuring the connector.
</Step>
<Step>
Click **Create**.
</Step>
<Step>
Go to the **Policies** tab and click **Modify**.

1. Scroll down to the **OAuth Policies** section. Under **Plugin Policies**, set **Permitted Users** to **Admin approved users are pre-authorized**.

2. After changing that setting, scroll back up to the **App Policies** section. Under **Select Profiles**, move the profile of your connector user (for example, **System Administrator**) from the available list to the selected list.

Click **Save**.
</Step>
<Step>
Go to the **Settings** tab, expand **OAuth Configuration**, and click **Consumer Key and Secret** to retrieve your **Consumer Key**. Save it — this is your Client ID.
</Step>
</Steps>

**Done.** You now have a `private.pem` file and a Consumer Key to use with the JWT Bearer authentication method.

### Create a Salesforce External Client App for Client Credentials

Use these instructions if you want to authenticate using a client ID and secret.

<Steps>
<Step>
Log into Salesforce as an Administrator. Click the gear icon and select **Setup**.
</Step>
<Step>
Search for "External Client App Manager" and select **External Client App Manager**.
</Step>
<Step>
Click **New External Client App**.
</Step>
<Step>
Fill in the basic information:
- **External Client App Name**: a name of your choice (for example, `baton-cc`)
- **Contact Email**: your email address
</Step>
<Step>
Expand **OAuth Settings** and configure the following:
- **Callback URL**: enter any valid URL
- **Selected OAuth Scopes**: add **Full access (full)** and **Manage user data via APIs (api)**
- Under **Flow Enablement**, check **Enable Client Credentials Flow**
</Step>
<Step>
Click **Save**.
</Step>
<Step>
Go to the **Policies** tab and click **Modify**.

Scroll down to the **OAuth Policies** section and find the **OAuth Flows and External Client App Enhancements** subsection:

1. Check **Enable Client Credentials Flow**. A **Run As (username)** field will appear directly below.
2. In the **Run As (username)** field, enter the Salesforce username of your connector user.

Click **Save**.
</Step>
<Step>
Go to the **Settings** tab, expand **OAuth Configuration**, and click **Consumer Key and Secret** to retrieve your **Consumer Key** and **Consumer Secret**. Save both — these are your Client ID and Client Secret.
</Step>
</Steps>

**Done.** You now have a Consumer Key and Consumer Secret to use with the Client Credentials authentication method.

<Steps>

<Step>
Click **Add**. The connector is created and its configuration page opens.

<Step>
Find the **Settings** area of the page and click **Edit**.
</Step>
<Step>
Select your method of authenticating to Salesforce: **OAuth**, **JWT Bearer**, **Client Credentials**, or **Username and password (deprecated) **.
</Step>
<Step>
   If you chose **OAuth**: 
      
      1. In the **Domain** field, enter your Salesforce domain.
      
      2. **Optional.** Check the box to tell C1 to use Salesforce usernames as the email addresses for your organization's accounts. This option is especially helpful if your organization uses multiple service accounts that all share a `noreply@salesforce.com` email address.

      3. **Optional.** Check the box if you want the connector to sync connected apps. 

      4. **Optional.** Uncheck the box if you do not want to sync deactivated users. 

      5. **Optional.** Check the box if you want the connector to sync users on non-standard licenses, such as external users. 

      6. **Optional.** Create a map of the Salesforce license types used by your organization and the profile associated with each license type that has the fewest permissions. C1 will use this information when deprovisioning user profiles to automatically reassign the user to the least-privilege profile associated with their license type. Each key is a Salesforce User License name and each value is a Profile name, not their IDs. Revoking a profile from a user whose license is not in the map fails.  

      7. Click **Save**. 

      8. Click **Login with OAuth**.

      9. Log in and authorize C1 with your Salesforce instance.

      10. You will then be redirected back to the Salesforce setup page in C1, where you'll see an authorization message.

      <Note>Salesforce limits refresh token idle lifetime to 30 days, in force in production since November 4, 2026. A connector that syncs on a schedule refreshes well inside that window. If a connector sits idle for longer than 30 days, re-authorize it with **Login with OAuth**. Salesforce also ends support for Connected Apps in Summer '27 in favour of External Client Apps; that migration is handled on the C1 side and needs no change to your connector configuration.</Note>

   If you chose **JWT Bearer**:

      1. In the **Domain** field, enter your Salesforce domain.

      2. In the **Client ID** field, enter the Consumer Key from your External Client App.

      3. In the **Private Key (.pem)** field, upload your `private.pem` file.

      4. In the **JWT Subject** field, enter the Salesforce username of the connector user.

      5. **Optional.** In the **Login URL** field, enter a custom Salesforce login URL. Defaults to `https://login.salesforce.com`. Use `https://test.salesforce.com` for sandbox orgs.

      6. **Optional.** Configure sync options as needed (connected apps, deactivated users, non-standard users, license mapping).

      7. Click **Save**.

   If you chose **Client Credentials**:

      1. In the **Domain** field, enter your Salesforce domain.

      2. In the **Client ID** field, enter the Consumer Key from your External Client App.

      3. In the **Client Secret** field, enter the Consumer Secret from your External Client App.

      4. **Optional.** Configure sync options as needed (connected apps, deactivated users, non-standard users, license mapping).

      5. Click **Save**.

   If you chose **Username and password (deprecated)**:

      <Warning>Username and password authentication is deprecated. It uses the Salesforce SOAP API `login()` call rather than an OAuth flow, so it is governed by Salesforce's SOAP login changes and not by the OAuth 2.0 username-password retirement: from **December 1, 2026** the connector user needs the **Use Any API Auth** system permission, which you can test ahead of time from **Setup** > **Release Updates**, and `login()` retires in **Summer '27** across API versions 31.0 through 64.0. Salesforce also lets an org disable `login()` ahead of that date, through **Enable SOAP API login()** under **Setup** > **User Interface** and through the retirement's test run under **Setup** > **Release Updates**. Use JWT Bearer or Client Credentials instead; Salesforce directs customers to external client apps, which is what those two methods use.</Warning>

      1. Enter your Salesforce username and password in the top two fields. 

      2. Enter your Salesforce security token in the **Security token** field. A C1-hosted connector always needs this token, because it connects from C1's network rather than from yours. The token is optional only for a self-hosted connector running inside a trusted IP range you have configured in Salesforce. The token is part of every login, so re-enter it here whenever the connector account's password changes. To obtain it, refer to [Reset Your Security Token](https://help.salesforce.com/s/articleView?id=xcloud.user_security_token.htm&type=5) in the Salesforce documentation. 

      3. In the **Domain** field, enter your Salesforce domain.
      
      4. **Optional.** Check the box to tell C1 to use Salesforce usernames as the email addresses for your organization's accounts. This option is especially helpful if your organization uses multiple service accounts that all share a `noreply@salesforce.com` email address.

      5. **Optional.** Check the box if you want the connector to sync connected apps. 

      6. **Optional.** Uncheck the box if you do not want to sync deactivated users. 

      7. **Optional.** Check the box if you want the connector to sync users on non-standard licenses, such as external users. 

      8. **Optional.** Create a map of the Salesforce license types used by your organization and the profile associated with each license type that has the fewest permissions. C1 will use this information when deprovisioning user profiles to automatically reassign the user to the least-privilege profile associated with their license type. Each key is a Salesforce User License name and each value is a Profile name, not their IDs. Revoking a profile from a user whose license is not in the map fails. 

      9. Click **Save**.
  </Step>
  <Step>
   The connector's label changes to **Syncing**, followed by **Connected**. You can view the logs to ensure that information is syncing.
  </Step>
</Steps>

**Done.** Your Salesforce connector is now pulling access data into C1.

### Step 2: Create Kubernetes configuration files

Create two Kubernetes manifest files for your Salesforce connector deployment:

#### Secrets configuration

```yaml expandable
# baton-salesforce-secrets.yaml
apiVersion: v1
kind: Secret
metadata:
  name: baton-salesforce-secrets
type: Opaque
stringData:
  # C1 credentials
  BATON_CLIENT_ID: <C1 client ID>
  BATON_CLIENT_SECRET: <C1 client secret>
  
  # Salesforce credentials
  BATON_INSTANCE_URL: <Salesforce domain>
  BATON_SALESFORCE_PASSWORD: <Password to the Salesforce account>
  BATON_SALESFORCE_USERNAME: <Username for the Salesforce account>
  BATON_SECURITY_TOKEN: <Salesforce security token (optional only when this host is inside a trusted IP range)>

  # Salesforce credentials, JWT Bearer. Use these instead of the username and password above.
  # BATON_AUTH_METHOD: jwt-bearer-group
  # BATON_SALESFORCE_CLIENT_ID: <Consumer Key from your External Client App>
  # BATON_SALESFORCE_PRIVATE_KEY: <contents of your private.pem, not a path to it>
  # BATON_SALESFORCE_JWT_SUBJECT: <Salesforce username of the connector user>
  # BATON_SALESFORCE_LOGIN_URL: <defaults to https://login.salesforce.com; use https://test.salesforce.com for sandbox orgs>

  # Salesforce credentials, Client Credentials. Use these instead of the username and password above.
  # BATON_AUTH_METHOD: client-credentials-group
  # BATON_SALESFORCE_CLIENT_ID: <Consumer Key from your External Client App>
  # BATON_SALESFORCE_CLIENT_SECRET: <Consumer Secret from your External Client App>

  # Optional: include if you want C1 to provision access using this connector
  BATON_PROVISIONING: true

  # Optional: include if you want to sync access to connected apps
  BATON_SYNC_CONNECTED_APPS: true

  # Optional: include if you DO NOT want to sync deactivated users (default = true)
  BATON_SYNC_DEACTIVATED_USERS: false

  # Optional: include if you want to sync accounts that use non-standard licenses
  BATON_SYNC_NON_STANDARD_USERS: true

  # Optional: include to use Salesforce usernames as the email addresses for your organization's accounts
  BATON_USER_USERNAME_FOR_EMAIL: true

  # Optional: include to provide info on how to manage least privileged profile changes 
  BATON_LICENSE_TO_LEAST_PRIVILEGED_PROFILE_MAPPING: <[map]>
```

Run `--help` to see all available configuration flags and environment variables.

```yaml expandable
# baton-salesforce.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: baton-salesforce
  labels:
    app: baton-salesforce

  selector:
    matchLabels:
      app: baton-salesforce

        - secretRef:
            name: baton-salesforce-secrets
```

## Troubleshooting the Salesforce integration

### When I try to log in with OAuth, I see a "This feature is not currently enabled for this user" error

Salesforce returns this error if the user who is logging in with OAuth does not have permission to access the Salesforce APIs: 

```bash
{"code":2, "message":"error getting info from connectorClient: [simpleforce] Error. http code: 403 Error Message:  This feature is not currently enabled for this user. Error Code: FUNCTIONALITY_NOT_ENABLED"}
```

If you see this message, follow the instructions to [Enable API access and permissions for your Salesforce user](/baton/salesforce#enable-api-access-and-permissions-for-your-salesforce-user) and then try logging in again.

### When I log in with a username and password, I see an "Invalid username, password, security token" error

Salesforce returns the same message for three different causes, and it names the credential in all three:

```bash
INVALID_LOGIN: Invalid username, password, security token; or user locked out
```

The credential is often not the problem. Check **Setup** > **Login History** for the failed attempt, which names the real cause:

| Login History status | What to do |
| :--- | :--- |
| `Failed: SOAP Login Disabled` | `login()` is disabled in the org. Check **Enable SOAP API login()** under **Setup** > **User Interface**, and the SOAP `login()` retirement test run under **Setup** > **Release Updates** |
| `Failed: API security token required` | Add the connector account's security token to the **Security token** field |
| `Invalid Password` | The password is wrong or has been reset |

### When I try to sync, I see an "insufficient access rights on cross-reference id" error

Salesforce returns this error if the connector user does not have sufficient permissions:

```bash
{"error": "error: listing resources failed: rpc error: code = InvalidArgument desc = 400 Bad Request\n[simpleforce] Error. http code: 400 Error Message:  insufficient access rights on cross-reference id Error Code: INSUFFICIENT_ACCESS"}
```

Create a Permission Set with the following system permissions and assign it to the connector user:

**Required system permissions for sync:**

| Permission | Purpose |
| :--- | :--- |
| API Enabled | Access Salesforce APIs |
| Manage Users | Read users and setup objects, and add and remove users from public groups |
| Customize Application | Required only if syncing connected apps |
| Use Any API Auth | Required only if authenticating with a username and password. Allows authentication via SOAP API `login()` when SOAP login access is restricted by the org |

**Additional permissions required for provisioning:**

| Permission | Purpose |
| :--- | :--- |
| Manage Roles | Assign and revoke role assignments |
| Manage Territories | Add and remove users from territories (only required if Enterprise Territory Management 2.0 is enabled) |

To fix this error, follow the instructions to [Enable API access and permissions for your Salesforce user](/baton/salesforce#enable-api-access-and-permissions-for-your-salesforce-user) to create a Permission Set with the required permissions and assign it to the connector user.
